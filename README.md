# Ren'Py File Compressor

A GUI tool for shrinking the on-disk footprint of Ren'Py games. It converts images to AVIF, re-encodes videos to VP9, patches the game's script files to match, and deploys a small runtime loader so Ren'Py can actually read the new formats — all without touching the original files until you confirm everything worked.

Built around the RPA-3.0 archive format that Ren'Py uses to pack assets.

---

## Requirements

**Python packages:**
```
customtkinter>=5.2
Pillow>=10.0
pillow-heif>=0.13
```

Install with:
```bash
pip install -r requirements.txt
```

**System dependency:** `ffmpeg` needs to be on your PATH (used for video encoding and as a fallback AVIF decoder at runtime).

On Ubuntu/Debian:
```bash
sudo apt install ffmpeg
```

---

## Running it

```bash
python main.py
```

That's it. A wizard window opens and walks you through the rest.

## Usage

The tool is a four-step wizard.

**Step 1 — Welcome**
Just an overview of what's about to happen. Click Next.

**Step 2 — Folder selection**
Point it at the root folder of your Ren'Py game (the one that contains the `game/` subdirectory). Two options here:

- *Create backups* — enabled by default. Renames each `.rpa` to `.rpa.bak` before replacing it. Safe to disable once you've verified everything works, since those backups take up a lot of space.
- *CPU threads* — how many cores to use for parallel image conversion. "Most" (all cores minus two) is the default and leaves the system responsive while compressing. "All" will pin every core.

**Step 3 — Compression**
Runs automatically. You'll see a live log of every file being processed, per-archive progress bars, ETA, and running savings totals. There's a Cancel button that aborts cleanly — nothing is written to disk until all archives finish staging.

**Step 4 — Done**
Shows a table of original vs. compressed size per archive and the total savings. After this, launch the game once so Ren'Py can recompile the patched `.rpy` scripts to `.rpyc`.

## How it works

### Archive format

Ren'Py packs game assets into `.rpa` archives using the RPA-3.0 format. The format is fairly simple: a text header contains an offset to the index and an XOR key. The index itself is a zlib-compressed pickle of `{filename: [(offset, length, prefix)]}`. The tool reads and writes this format directly without going through Ren'Py.

### Images

Every `.png`, `.webp`, `.jpg`, `.jpeg`, `.bmp`, and `.tga` file outside `gui/` gets converted to AVIF using `pillow-heif`. The quality setting is 85 with chroma 4:4:4 — visually lossless at roughly half the file size of a well-compressed PNG, sometimes much less. If the AVIF output would actually be *larger* than the original (rare, but happens with tiny images), the original is kept.

`gui/` images are intentionally skipped. Their paths get compiled into Ren'Py's `.rpyc` bytecode at build time and can't be patched without a Ren'Py SDK. Converting them would just break the GUI.

### Videos

Videos are re-encoded to VP9/Opus in a WebM container using ffmpeg. The encode settings are CRF 33 (constant quality), `-deadline good`, `-cpu-used 4`, with row-based multithreading (`-row-mt 1`) enabled for a significant speedup on multi-core CPUs. AV1 was the original target codec but Ren'Py's statically-linked FFmpeg build doesn't include an AV1 decoder, so VP9 it is.

### Script patching

After converting images in an archive, the tool builds a map of `original_path → new_path` (e.g. `images/char/lucy.png → images/char/lucy.avif`). This map is applied to all `.rpy` source files across the archive using a simple byte-level find-and-replace. Compiled `.rpyc` files are kept intact — they get regenerated by Ren'Py on next launch from the patched `.rpy` sources.

The path map is accumulated globally across all archives so that scripts in one archive can correctly reference images converted in a different one.

### Runtime AVIF support

Ren'Py has no native AVIF support, so the tool deploys a script (`hhg_avif_support.rpy`) to the game's `game/` directory. This script runs at `init -999` priority (very early in the startup sequence) and monkey-patches two internal Ren'Py functions:

- `renpy.loader.load` — intercepts file load requests. If a `.png` (or similar) is requested but not found, it tries the equivalent `.avif` path instead. This handles cases where `.rpyc` bytecode has hardcoded paths that couldn't be patched.
- `renpy.display.pgrender.load_image` — intercepts image decoding. Detects AVIF files by magic bytes (`data[4:8] == b'ftyp'`) regardless of filename extension and routes them through a decoder.

For decoding, the script spawns a persistent subprocess running `pillow-heif` on the system Python (not Ren'Py's bundled Python, which doesn't have pillow-heif). The subprocess stays alive for the duration of the game session and communicates over stdin/stdout with a simple length-prefixed binary protocol. This keeps decode latency around 30ms per image instead of the ~200ms you'd pay spawning a fresh ffmpeg process each time. ffmpeg is still used as a fallback if the worker isn't available.

A second block at `init 1901` scans all files in the archives after Ren'Py's own image auto-detection pass (which runs at init 0) and registers any `.avif` files it finds under their base name, so `show lucy` and similar commands continue to work.

### Staging and atomic swap

Nothing gets written to the original files until all archives have been processed. Each output archive is written to a temporary staging directory first. Only once everything succeeds does the tool rename the originals to `.bak` and move the staged files into place. If you cancel mid-run or something throws an error, the staging directory is cleaned up and the originals are untouched.

## Notes

- The first game launch after compression takes slightly longer than usual because Ren'Py recompiles all the patched `.rpy` files to `.rpyc`. Subsequent launches are normal.
- Running the compressor a second time on an already-compressed game is safe but pointless for images (AVIF files aren't recognized as images, so they pass through unchanged). It will re-deploy the runtime support script, which is fine.
- The runtime support script is re-deployed on every successful compression run, so you don't need to worry about it going missing.
